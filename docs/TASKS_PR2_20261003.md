# PR2 — owner-approved business work purchases

This change extends the existing Tasks console and owner workspace. It is a
service-neutral purchase boundary, not a GPU application. The first admitted
worker cleans an operations/contact CSV: trim cell whitespace, preserve rows,
export JSON or spreadsheet-safe CSV. Other briefs remain saved/plannable; they
are not sold as finished AI services. No paid language-model task is installed.

## What executes

`typed task → frozen USD price/input/revision → owner approval → PayPal sandbox
order → buyer approval → capture → fresh order GET → exact full capture binding
→ one entitlement → deterministic transformation → owner-only download`

A frozen plan binds the admitted SKU version, merchant ID, exact USD price,
input hash, task revision, brief hash and expiry. The task's USD ceiling is
checked before payment. One active purchase per task prevents a second plan
from reusing the same budget; this is not an aggregate multi-task USD account.
API agents can read metadata but cannot create purchase plans, approve, capture,
reconcile, fulfill or download. Owner workspaces contain separate purchase rows.

Provider requests persist unique UUID operation keys and submission intent
before network I/O. Each mutation sends at most once. Unknown creation/capture
retains the task lock; it does not release funds or create a second order.
Capture response alone cannot grant access: fresh PayPal GET must show one
COMPLETED, final capture with matching order, merchant, currency, gross price,
reference ID and plan hash. APPROVED, redirects, pending/partial captures,
refunds and caller-posted paid claims cannot create an entitlement.

Paid work can resume fulfillment after restart without charging again. Results
are hash-bound and private/no-store. Editing or cancelling an unsent plan revokes
it; work with a provider intent or completed payment cannot be falsely cancelled
as unsent. Inputs stay in the owner's 0600 SQLite database and are omitted from
checkout metadata/events. CSV formula strings are escaped on CSV export;
JSON preserves data values. Transformation fidelity is not data truth.

## Configuration and account boundary

Only `https://api-m.sandbox.paypal.com` is implemented. There is no live-money
endpoint or frontend credential. Server requests use DNS-pinned HTTPS, bounded
responses, no redirects/retries and sanitized public errors. OAuth tokens remain
in request memory; client ID/secret are private environment references.

1. Owner signs into [PayPal Developer](https://developer.paypal.com/dashboard/applications/sandbox).
   A real owner's financial account and legal identity cannot be fabricated by
   the implementation. Account signup, credential entry and legal consent stay
   with the owner. Creating sandbox app/test identities is the next setup step
   after this login; it has not happened in this release.
2. Create a sandbox app for a sandbox Business seller and a separate Personal
   test buyer. Save secrets only in the private server service environment.
3. Copy `deploy/paypal-sandbox.example.json` into the project's private operator
   configuration directory, chmod 0600, replace the merchant placeholder with
   the **sandbox seller merchant ID**, and set the private client ID/secret env
   values. The example's USD 1.00 is a sample operator price, not a live vendor
   quote; admit the actual seller/SKU/price before enabling checkout.
4. Set `ENGINE_PAYPAL_SANDBOX_FILE` to that absolute private config path in the
   existing project's service environment. No other project's keys are used.
   Both private credentials must exist for checkout to report configured.
5. Owner creates a `data_cleanup` task with exact required column names and
   CSV/JSON output, reviews its frozen plan, continues to sandbox checkout and
   approves as the test buyer. Back in Tasks, confirm payment, prepare the
   result and download it. Record actual order/capture GET evidence separately.

The public runtime is intentionally unconfigured until these owner-account
steps finish. The PayPal login page has been opened for handoff. No actual
sandbox order/capture ID, test buyer account or merchant app is claimed here.

## Remaining PR3 boundaries

Verified webhooks, refund/cancellation transitions, operator recovery for a lost
create response without an order ID, stale checkout expiry cleanup and automatic
reconciliation workers are not installed. Unknown captures support owner GET
reconciliation only; they never automatically recapture. Capture-request keys
are persisted but not blindly retried outside PayPal's documented retention.
Paid access revocation following a later refund/dispute needs PR3 webhook/readback
handling; this release does not claim continuous entitlement monitoring.

First actual sandbox approval/capture/readback/delivery is still required for
PR2's real-provider acceptance. No production-ready or contest-submitted claim
follows from fixture tests. PR2 is stacked on open PR1 and remains a draft until
actual sandbox evidence exists.
