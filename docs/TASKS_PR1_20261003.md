# PR1 — practical work briefs in the existing Economic Machine console

Five work types: vendor comparison, research brief, document draft, data cleanup,
and content localization. The console's Tasks navigation writes to the same
owner workspace database and journal used by connections, named agents and
execution. This is a durable task foundation, not a second standalone console.

## Implemented contract

- Exact USD decimal strings become integer cents, with a $10,000 maximum.
  Zero-budget work is allowed. USD is not USDC, credits or venue USDT turnover.
- The user supplies task title, brief, deliverable and language/criteria. Free
  text cannot infer price, tomorrow's date, previous regions or consent.
- Optional connection IDs must belong to the active owner workspace. Disconnect
  invalidates dependent work; configuring a connection does not read that API.
- Immutable brief revisions, canonical hashes and optimistic revision checks.
  Concurrent edits cannot overwrite each other. Idempotency IDs bind operation
  and exact input; ambiguous network retries use the same saved client request.
- Confirmed preferences contain only selected conditions, scoped by work type,
  with an expiry and immutable version. Explicit conditions override remembered
  conditions. Budget, deadline, credentials, connections, instructions and
  approvals are never inherited. “Last” without valid context needs input.
- Revocation or expiry invalidates actually inherited conditions. Editing an
  effective field explicitly removes its dependence on that preference.
- Owner-only confirmation, revocation and unsent cancellation. Engine writer
  keys may draft/revise; reader keys cannot draft; task access grants no payment
  authority. Separate wallets and operators keep separate workspace databases.
- The optional operator-only `ENGINE_TASK_SERVICES_FILE` is a bounded versioned
  SKU catalogue with merchant, work type and exact USD price. Default is empty.
  Declared prices are explicitly unverified; no entry enables purchasing or
  fulfillment. Do not publish credentials or use customer-controlled paths.
- Restart-safe persistence, bounded task/revision counts and body hash checks.
  Journal events bind result/input hashes and contain no raw task instructions.

## API and state semantics

`GET/POST /api/engine/tasks`, `GET /api/engine/tasks/{id}`,
`POST /api/engine/tasks/{id}/revise`, owner-only `.../remember`, `.../cancel`,
and `/api/engine/task-preferences/{id}/revoke`. Shared route factory works in
both wallet-hosted and loopback owner-token deployments. All reads are scoped.

Brief states: `NEEDS_INPUT`, `READY_TO_PLAN`, `EXPIRED`, `CANCELLED_UNSENT`.
`READY_TO_PLAN` means the brief is complete. It does not mean a provider exists,
research is done, capital is reserved, a plan is approved or a job has run.
Mutation replays return the exact historical mutation receipt. A fresh GET
re-evaluates expiry, revoked preferences and disconnected connections. Future
execution must use a fresh current-state and exact-plan approval check.

The console preserves unsaved edits during its background refresh, retains
request IDs after ambiguous saves and clears drafts when owner identity changes.
Typed deadline inputs use the user's displayed local time; the stored instant
is epoch seconds. No background work is started by saving a task or preference.

## Validation boundary

Build/test/browser work is restricted to the authorized Canadian server. The
existing native library is copied into the isolated checkout for unchanged ABI
connection regressions; symlink libraries are intentionally rejected. No native
source rebuild or repeat of the old complete commerce suite is necessary.

Focused tests cover tasks, credentials, portal assets and affected workspace /
agent-control initialization. Browser acceptance covers real form → API → DB →
reload, preference reuse and revocation, practical work types and responsive
layout. Public checks use an unfunded disposable wallet's login message only.
Evidence is under `artifacts/tasks-pr1`; failed initial checks remain recorded.

## Portal connection correction

The real public browser exposed HTTP 503 responses on simultaneous asset loads:
Uvicorn's 16-connection bound also counted idle keep-alive connections. The
portal-only deployment override uses 64 bounded connections/backlog, a two-second
keep-alive and 64 maximum OS tasks. Its existing 256-MiB service memory ceiling
and native-work semaphore remain unchanged. Payment API admission and signing
rules are untouched. This corrects asset loading; it is not a multi-user soak or
production capacity certification. Initial failed browser logs remain available.

## Next boundaries

buyer approval, capture/readback and entitlement. PR3 handles uncertain capture,
webhooks, recovery and refunds. PR4 exposes scoped MCP tools. PR5 performs bounded
